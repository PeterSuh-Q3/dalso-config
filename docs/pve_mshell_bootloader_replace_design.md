# 기존 Proxmox VM의 m-shell 부트로더 이미지 교체 설계

## 목적과 산출물

- 구현할 셸 스크립트 이름: 저장소 루트의 `pve_mshell_bootloader_replace.sh`
- 이 문서는 구현 전 설계서다. 현재 커밋에는 실행 스크립트를 포함하지 않는다.
- 기존 VM을 선택해 연결된 m-shell 부트로더 `.img`를 최신 릴리스 이미지로 교체한다.
- 원본 이미지의 세 번째 파티션(P3) 루트에 있는 `/user_config.json`을 새 이미지의 P3 루트에 복사한다. 이 파일 복사만으로 설정이 적용되며, 로더 재빌드는 수행하지 않는다.
- RR 부트로더는 지원하지 않는다. 새 VM 생성, DSM 데이터 디스크 변경, 자동 VM 시작도 범위 밖이다.

## 전제와 실행 환경

- Proxmox VE 호스트에서 `root`로 대화형 실행한다. VM과 원본 이미지가 현재 호스트에서 접근 가능해야 한다.
- 대상은 원본 `pve_xpenol_install.sh`와 같은 방식으로 `qm`의 `args`에 `-drive if=none,id=synoboot,format=raw,file=...` 및 해당 USB 장치가 연결된 QEMU VM이다.
- VM은 이미 중지되어 있어야 한다. 실행 중이거나 잠긴 VM은 변경하지 않는다. 스크립트가 종료하거나 시작하지 않는다.
- 원본과 새 이미지 모두 일반 파일 형태의 raw `.img`이며, P3를 식별할 수 있어야 한다. 블록 장치, 스토리지 볼륨 ID, qcow2, 스냅샷 이미지는 지원하지 않는다.
- 필요한 도구는 `qm`, `pvesh`, `jq`, `whiptail`, `curl`, `gzip`, `losetup`, `mount`, `umount`, `findmnt`, `sha256sum`, `sync` 등이다. 누락되면 변경 전에 알리고 종료한다. 실행 중 패키지를 자동 설치하지 않는다.

## 사용자 흐름

1. 로컬 노드의 VM 목록에서 `synoboot` 매핑이 확인된 VM의 VMID, 이름, 실행 상태, 이미지 경로를 표시한다. 이 단계에서 모호한 `args` 구성이나 m-shell로 판별할 수 없는 이미지는 선택 대상에서 제외하고 이유를 표시한다.
2. 한 VM을 선택한다. `qm config`와 `qm status`를 다시 읽어 VM이 중지되었고 설정이 선택 당시와 같은지 확인한다.
3. 원본 이미지의 P3를 읽기 전용으로 마운트해 `/user_config.json`을 추출한다. `jq`로 JSON 문법을 확인하고 SHA-256 해시를 기록한다. 파일이 없거나 읽을 수 없으면 중단한다.
4. `PeterSuh-Q3/tinycore-redpill`의 최신 릴리스 태그를 조회하고 원본 설치 스크립트와 같은 이름 규칙인 `alpine-redpill.<tag>.m-shell.img.gz`를 다운로드한다. 압축 파일과 해제된 이미지가 정상인지 확인한다. 검증 가능한 공식 체크섬이 릴리스에 있으면 함께 검증한다.
5. 새 이미지를 **기존 이미지와 다른 고유한 파일 경로**에 준비한다. 기존 파일을 덮어쓰지 않는다. 새 이미지의 P3를 쓰기 가능으로 마운트한 뒤 `/user_config.json`을 임시 파일로 복사하고 최종 이름으로 바꾼다.
6. 새 P3에서 파일을 다시 읽어 원본 설정 파일과 SHA-256 해시가 같은지 확인한다. 기록을 동기화하고 정상적으로 마운트 해제한 뒤, 이미지 파일을 재연결하여 P3의 `/user_config.json`을 읽기 전용으로 재검증한다.
7. VMID, 원본/새 이미지 경로, 릴리스 태그, 설정 파일 해시, `args` 변경 내용을 사용자에게 보여주고 최종 실행 확인을 받는다.
8. VM 상태와 설정을 한 번 더 확인한 후 `synoboot` 드라이브의 `file=` 값만 새 이미지 경로로 바꾼다. 다른 QEMU 인수는 유지한다. `qm set <VMID> --args ...` 실행 뒤 `qm config`에서 새 경로가 반영되었는지 확인한다.
9. 결과, 원본 이미지 경로, 복원 명령의 근거가 되는 원본 `args` 값을 출력한다. VM은 중지 상태로 둔다.

## 이미지 및 설정 파일 처리

- 원본 이미지는 어떠한 단계에서도 쓰기 가능으로 마운트하지 않는다.
- 원본 `args`에서 정확히 하나의 `id=synoboot` 드라이브와 그 `file=` 경로를 찾아야 한다. 둘 이상이거나 인수 구조를 안전하게 해석할 수 없으면 중단한다. 임의의 `file=`이나 다른 장치 인수를 치환하지 않는다.
- m-shell 판별은 원본 파일명만으로 하지 않는다. 원본 P3의 `/user_config.json` 존재 및 유효성을 확인한다. 이 검사만으로 다른 로더를 확실히 구별할 수 없는 구성은 지원 범위에서 제외한다.
- 새 이미지의 파티션 테이블에서 **세 번째 파티션만** 대상으로 삼는다. 파티션 식별이 모호하면 중단한다. 호스트의 물리 디스크를 대상으로 삼지 않도록 loop 장치가 선택한 `.img`에 연결됐는지 확인한다.
- 새 P3에 이미 `/user_config.json`이 있다면 새 이미지 내부의 임시 백업 파일로 보관한 후 교체한다. 설치 후 이 백업을 보존할 필요가 없다면 구현 단계에서 정리할 수 있으나, 교체 전에는 지우지 않는다.
- 파일 복사 후 해시 일치, `sync`, `umount`, 읽기 전용 재마운트 검증 중 하나라도 실패하면 `qm set`을 실행하지 않는다.
- `trap`으로 임시 마운트와 loop 장치를 정리한다. 정리 실패는 성공으로 처리하지 않고 수동 정리 대상 장치를 출력한다.

## 저장 위치와 보존 정책

- 새 `.img`는 원본 이미지와 같은 호스트의 동일 디렉터리에 VMID·릴리스 태그·고유 식별자를 포함한 이름으로 저장한다. 충분한 여유 공간과 쓰기 권한을 먼저 확인한다.
- 원본 이미지는 삭제하거나 이름을 변경하지 않는다. 다른 VM이 같은 원본 파일을 참조해도 영향을 주지 않는다.
- 작업 중간 파일은 새 최종 이미지와 구별되는 이름으로 생성한다. 검증이 끝나기 전에는 VM이 참조하지 않는다.
- 원본 VM 설정(`qm config` 출력)과 적용 전후 이미지 경로, 설정 해시를 작업 기록으로 남긴다. `user_config.json`에는 민감한 설정이 있을 수 있으므로 기록 파일은 root만 읽을 수 있게 하고 설정 내용 자체는 로그에 출력하지 않는다.
- 완료 후에도 원본 이미지를 자동 정리하지 않는다. 복원은 중지된 VM에서 보관한 원본 `args`를 다시 적용하는 방식이다.

## 실패 시 동작

| 단계 | 동작 |
| --- | --- |
| 선택·상태·원본 검사 실패 | 이미지와 VM 설정을 변경하지 않고 종료 |
| 다운로드·압축 해제·P3 복사·검증 실패 | VM 설정을 변경하지 않고 임시 자원을 정리; 원본 이미지 유지 |
| `qm set` 실패 또는 적용 결과 불일치 | 보관한 원본 `args`로 설정 복원을 시도하고 재검증; 복원 실패 시 정확한 원본/현재 설정을 출력하고 오류 종료 |
| 복사 완료 후 마운트 해제 실패 | VM 설정을 변경하지 않고 마운트/loop 장치 정보를 출력하여 수동 정리 가능하게 함 |

전원 켜짐, VM 잠금, 원본 `args` 변경, 이미지 파일 변경이 작업 중 감지되면 적용을 중단한다. 새 이미지 준비 중에도 원본 이미지 파일의 식별 정보와 설정 해시를 적용 직전에 다시 확인한다.

## 구현 완료 기준

- 중지된 m-shell VM 하나를 선택해 최신 `.img`로 연결 경로를 교체할 수 있다.
- 원본 P3 `/user_config.json`과 새 P3 `/user_config.json`의 내용이 동일하다.
- 원본 이미지 및 VM의 데이터 디스크는 수정되지 않는다.
- `args`의 `synoboot` 파일 경로 외 설정은 그대로다.
- 복사·마운트·설정 변경 실패 시 기존 VM 설정으로 돌아가거나 수동 복원에 필요한 값을 출력한다.
- VM은 자동으로 시작하지 않는다.

## 구현 시 검증 계획

- `bash -n` 및 정적 분석으로 셸 문법과 인수 인용을 확인한다.
- 임시 raw 이미지 2개로 P3 추출·복사·해시 검증·마운트 정리를 시험한다.
- `qm` 명령을 모의 실행해 실행 중 VM, 모호한 `args`, 다운로드 실패, 마운트 실패, 검증 실패, `qm set` 실패와 복원을 확인한다.
- 실제 Proxmox VM에서의 부팅 성공 여부는 구현 테스트 환경에서 확인해야 하며, 파일 복사와 VM 설정 검증만으로 DSM 부팅까지 보증하지 않는다.
